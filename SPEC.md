# Специфікація: AI Support Drafts

Сервіс приймає звернення з хелпдеску через вебхук, у фоні готує чернетку відповіді за допомогою LLM на основі бази знань, дає оператору підтвердити або відхилити її і надсилає підтверджену відповідь клієнту через API хелпдеску.

## 1. Стек

| Компонент | Вибір | Навіщо |
|---|---|---|
| API та UI оператора | FastAPI + Jinja2 | Async, простий серверний HTML без фронтенд-збірки |
| БД | PostgreSQL 16 + SQLAlchemy 2.0 + Alembic | API — async (asyncpg), Celery-воркер — sync (psycopg); моделі спільні |
| Фонові задачі | Celery | Повтори, затримки, воркери «з коробки» |
| Брокер | RabbitMQ | Durable-черги, persistent-повідомлення, dead-letter |
| Rate limiter | Redis | Спільний лічильник LLM-запитів на весь сервіс |
| Пошук по базі знань | PostgreSQL full-text search | Працює без API-ключа (embeddings його потребують) |
| LLM | OpenAI (модель у `.env`) | Провайдер на вибір |
| Мок хелпдеску | Окремий FastAPI-сервіс | Імітує 5xx, таймаути, дедуплікацію |
| Запуск | docker compose | `docker compose up` |
| Пакети / лінтер | uv, ruff | |

## 2. Сервіси docker compose

- `api` — FastAPI: вебхук, UI оператора, `/health`.
- `worker` — Celery-воркер.
- `beat` — Celery beat (періодичний «підбирач» застряглих звернень).
- `postgres`, `rabbitmq`, `redis`.
- `helpdesk-mock` — мок хелпдеску.
- `migrate` — одноразовий запуск Alembic + наповнення бази знань.

## 4. Статуси звернення

```
received → generating → drafted → approved → sending → sent
                 │                    │           │
                 └→ generation_failed └→ rejected └→ send_failed
```

Усі переходи — атомарні умовні `UPDATE ... WHERE status = <очікуваний> RETURNING ...`. Якщо оновлено 0 рядків — хтось інший уже обробив перехід, задача тихо завершується. Це основний захист від подвійної обробки.

## 5. Потоки

### 5.1 Вебхук `POST /webhooks/helpdesk`
1. Валідація тіла (Pydantic).
2. `INSERT INTO tickets ... ON CONFLICT (event_id) DO NOTHING RETURNING id`.
3. Якщо рядок вставлено — після коміту поставити в чергу `generate_draft(ticket_id)`. Публікація не блокує відповідь: виконується поза event loop, з таймаутом з'єднання з брокером 1 с, одним коротким повтором і жорсткою межею 1,5 с. Якщо публікація не вдалася — лог помилки, відповідь все одно `202`.
4. Повернути `202 Accepted` в обох випадках (новий і дублікат) — хелпдеск не повинен повторювати доставку дубліката.

**Чому так:**
- Вебхук не викликає LLM і не чекає воркерів — відповідь за мілісекунди, з запасом до ліміту 2 с.
- Дедуплікація на рівні БД (unique-індекс) працює навіть для одночасних однакових подій; перевірка «чи існує» в коді — ні.
- Спершу коміт у БД, потім публікація задачі. Якщо публікація впала після коміту — звернення лишається `received`, його підбере `beat` (§5.5). Звернення не губляться.

### 5.2 Генерація чернетки (Celery-задача `generate_draft`)
1. `UPDATE status='generating' WHERE id=:id AND status='received'` — якщо 0 рядків, вихід.
2. Пошук топ-3 статей по `search_vector`: слова звернення (нижній регістр, лише літери й цифри) коротші за 3 символи відкидаються, решта скорочується до перших 5 символів і з'єднується через OR з префіксним збігом: `to_tsquery('simple', 'експо:* | pdf:* | звіт:*')`. Сортування за `ts_rank`. `websearch_to_tsquery` не підходить: він з'єднує слова через AND, а звернення — ціле речення, тож результатів майже завжди нуль. Конфіг `simple`, бо українського словника в Postgres немає; скорочення до основи компенсує відмінювання («експортувати» знаходить «експорт»).
3. Отримати дозвіл rate limiter'а (§6). Якщо ліміт вичерпано — це не помилка: `generating → received` і `retry` з `countdown` до наступного вікна; спроба не рахується.
4. `attempts_generate += 1` (коміт до виклику, щоб падіння воркера теж рахувалося як спроба), виклик LLM (§7) з промптом: відповідати тільки з наданих статей, додати посилання на них, якщо відповіді немає — так і сказати.
5. Зберегти `draft`, `draft_sources`, `status='drafted'`.
6. Тимчасова помилка (таймаут, мережа, 5xx, 429, невалідна відповідь) або неочікуваний виняток → `retry` з експоненційною затримкою (база 5 с, максимум 300 с, jitter); коли `attempts_generate` досягає `MAX_GENERATE_ATTEMPTS` → `generation_failed` + `last_error`. Ліміт рахується по колонці в БД, а не через `max_retries` Celery (у задачі `max_retries=None`), бо відмови лімітера не повинні з'їдати спроби. Постійна помилка (4xx, крім 429) → одразу `generation_failed`.
7. Перед кожним `retry` статус повертається умовним `UPDATE status='received' WHERE id=:id AND status='generating'`, щоб повторна спроба пройшла крок 1 так само, як перша. Якщо цей `UPDATE` оновив 0 рядків — `retry` не робиться, лог і вихід.

Налаштування Celery: `acks_late=True`, `task_reject_on_worker_lost=True`, `worker_prefetch_multiplier=1`. Падіння воркера посеред задачі повертає повідомлення в чергу.

### 5.3 Модерація (UI оператора)
- `GET /operator` — список звернень зі статусами, повідомленням клієнта, чернеткою і джерелами.
- `POST /operator/tickets/{id}/approve` — оператор може відредагувати текст; `UPDATE status='approved', final_message=... WHERE status='drafted'`; поставити в чергу `send_reply`.
- `POST /operator/tickets/{id}/reject` — `status='rejected'`.
- Інтерфейс базовий: Jinja2 + мінімальний CSS, без уваги до дизайну.

### 5.4 Надсилання (Celery-задача `send_reply`)
1. `UPDATE status='sending' WHERE id=:id AND status IN ('approved','sending')` — повтор після збою знову бере `sending`.
2. `POST <reply_url>` з тілом `{ticket_id, message}` і заголовком `Idempotency-Key: <ticket.id>`, таймаут ~5 с.
3. `201` → `status='sent'`.
4. 5xx / таймаут / мережева помилка → `retry` з експоненційною затримкою; після N спроб → `send_failed`.
5. 4xx (крім 409/429) → без повторів, `send_failed`.

**Захист від подвійної відповіді клієнту:**
- Атомарний перехід статусу — дві задачі не надсилають одночасно.
- `Idempotency-Key` — якщо хелпдеск прийняв відповідь, але ми не отримали `201` через таймаут, повтор не створить дубліката: мок повертає той самий `201` для вже відомого ключа.
- Обмеження чесно описано в README: якщо справжній хелпдеск не підтримує ідемпотентність, гарантія «рівно один раз» неможлива — лишається вибір між «не більше одного разу» і «щонайменше один раз».

### 5.5 «Підбирач» (Celery beat, раз на хвилину)
- `received` старше 1 хв → повторно поставити `generate_draft`.
- `generating` старше 5 хв (воркер, імовірно, впав) → повернути в `received`.
- `approved` / `sending` старше 2 хв без руху → повторно поставити `send_reply`.

Задачі ідемпотентні (§4), тож повторна постановка безпечна.

### 5.6 `GET /health`
Повертає `200 OK`. Опційно: перевірка з'єднання з БД.

## 6. Rate limiter (60 LLM-запитів/хв на весь сервіс)

- Вбудований `rate_limit` у Celery діє на кожен воркер окремо, а не на весь сервіс, тому не підходить.
- Redis, фіксоване вікно в 60 с: `INCR llm:rl:<поточна_хвилина>` + `EXPIRE 60`. Якщо значення > 60 — дозволу немає, задача робить `retry` на початок наступної хвилини.
- Пікове навантаження: 500 звернень / 10 хв = 50/хв — нижче ліміту. Черга RabbitMQ працює як буфер: при сплесках звернення чекають, а не губляться.
- Пропускна здатність воркера: пік 50 звернень/хв × ~17 с на LLM-виклик ≈ 15 одночасних задач. Задачі IO-bound, тому воркер запускається з `--pool=threads --concurrency=20`.

## 7. LLM-клієнт і режим без ключа

- Конфіг: `LLM_API_KEY`, `LLM_MODEL`, `LLM_TIMEOUT`.
- Є ключ → звичайний виклик, відповідь йде в чернетку.
- Немає ключа → сервіс **все одно робить реальний HTTP-запит** до провайдера (очікувано отримує 401), а потім повертає статичну відповідь, зібрану зі знайдених статей, із випадковою затримкою 5–30 с. Решта системи (rate limiter, повтори, статуси) працює однаково в обох режимах.

## 8. Мок хелпдеску (`helpdesk-mock`)

- `POST /tickets/{ticket_id}/replies` — приймає відповідь.
  - Конфігуровано: ~20% відповідей 5xx, ~10% — затримка довша за таймаут клієнта.
  - Дедуплікація за `Idempotency-Key`: повторний ключ → той самий `201`, без нового запису.
- `GET /replies` — список отриманих відповідей (для перевірки, що дублікатів немає).
- `scripts/send_webhooks.py` — шле звернення на вебхук, зокрема ту саму подію кілька разів одночасно, і пакет на 500 звернень для перевірки піку.

## 9. Конфігурація

`.env` (у репозиторії — `.env.example`): `DATABASE_URL`, `CELERY_BROKER_URL` (amqp://...), `REDIS_URL`, `LLM_API_KEY`, `LLM_MODEL`, `HELPDESK_TIMEOUT`, ліміти повторів. Секрети не комітимо.

## 10. Тести (pytest)

1. Дублікат вебхука (послідовно й одночасно) → один запис у БД, одна задача.
2. Вебхук відповідає швидко й не чекає LLM.
3. Rate limiter: 61-й запит у хвилині не проходить.
4. Надсилання: 5xx → повтор → `sent`; хелпдеск отримав рівно одну відповідь.
5. Подвійне підтвердження оператором → одне надсилання.
6. Режим без ключа: робиться реальний запит, повертається статична відповідь.

## 11. Етапи розробки (окремі гілки, коміт після кожного кроку)

9. `deploy` — розгортання й публічні посилання.
